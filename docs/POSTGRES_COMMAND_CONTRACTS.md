# PostgreSQL Command Contracts

Этот документ фиксирует, зачем нужен `src/postgres/booking-command-contracts.js`.
Файл не подключен к production runtime и не меняет поведение JSON-хранилища.

## Задача

Перед переносом `/api/state` и `/api/report` на PostgreSQL нужно не потерять
ни одну бизнес-команду:

- запись стажера;
- назначение даты;
- подтверждение рекрутом;
- рабочая группа;
- выход / невыход;
- отчет наставника;
- итог стажеру;
- откаты;
- отмены;
- изменение мест;
- опытный стажер;
- отчеты в Telegram-группы.

Контракт описывает для каждой команды:

- источник команды: `/api/state` или `/api/report`;
- допустимые роли;
- какие таблицы меняются;
- какие строки надо блокировать в транзакции;
- какие audit-события должны появиться;
- нужен ли `baseVersion`;
- нужен ли notification outbox;
- какой idempotency key нужен для защиты от двойной отправки.

## Почему Это Важно

Сейчас JSON-runtime защищается общей очередью `withBookingMutation`. В
PostgreSQL такой подход должен стать явными транзакциями и row-level locks.
Иначе вернутся старые классы багов:

- двойной клик создает дубль;
- отчет наставника отправляется в группу несколько раз;
- стажер не исчезает из списка наставника после финального отчета;
- дата закрывается раньше или позже нужного;
- Telegram-уведомление ушло, а state не сохранился;
- state сохранился, а Telegram-уведомление потерялось.

## Проверка

Тест `test/postgres-command-contracts.test.js` автоматически сверяет, что все
`case` внутри `applyBookingCommand` имеют Postgres-контракт. Если в будущем
появится новая `/api/state` команда без транзакционного плана, тест упадет.

Отдельно контракт фиксирует `mentor_report_result`, потому что отчет наставника
идет через `/api/report`, а не через `/api/state`. Это критичный путь: он меняет
статус стажера, закрывает дату при полном завершении и должен создавать
уведомление через outbox.
