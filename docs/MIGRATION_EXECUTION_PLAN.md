# Migration Execution Plan

Этот файл фиксирует конкретный порядок миграции `loft_hall_internship_unified`
с JSON `data/db.json` на PostgreSQL. Не хранить здесь секреты, токены,
пароли, chat id из `.env` или дампы персональных данных.

## Цель

Без простоя и потери цепочки перевести продакшен-проект на PostgreSQL:

```text
заявка -> подтверждение -> рабочая группа -> выход -> отчет наставника
-> итог стажеру -> реестр -> архив/история
```

Production до финального cutover не трогать. Все рискованные изменения сначала
проходят через отдельный migration staging:

- URL: `https://stazhirovka-migration.151.244.243.164.sslip.io`
- режим Telegram: `TELEGRAM_DELIVERY_MODE=dry_run`
- личные уведомления стажерам: `SUPPRESS_TRAINEE_NOTIFICATIONS=yes`

## Общий прогресс

Текущий общий прогресс: **55%**.

Правило оценки: процент считается от полной цели, где 100% означает, что
production работает на PostgreSQL, цепочка проверена, уведомления отслеживаются
через outbox, есть backup/rollback и обновленные handoff-документы.

Каждый следующий рабочий отчет по миграции должен начинаться с:

```text
Прогресс миграции: X%.
```

## Этапы

| Этап | Вес | Статус | Definition of Done |
| --- | ---: | --- | --- |
| 1. Safety baseline и документы | 5% | готово | Зафиксированы правила: прод не трогать, staging отдельно, Telegram dry-run. |
| 2. Postgres schema/import/read-only parity | 20% | готово | JSON импортируется в Postgres, обратное чтение совпадает с JSON, read-only staging поднят. |
| 3. Синхронизация с актуальным `main` | 10% | готово | Миграционная ветка содержит все свежие prod-фиксы, тесты проходят. |
| 4. Полный event log | 15% | в работе | Каждое бизнес-действие пишет понятное событие с actor, application, shift и payload. |
| 5. Writable Postgres command layer | 20% | в работе | Все команды `/api/state` работают транзакционно в Postgres staging без JSON-записи. |
| 6. Notifications/outbox | 15% | не начато | Telegram-сообщения создаются как записи `notifications`, worker отправляет и сохраняет результат. |
| 7. Full staging QA и rehearsal | 10% | не начато | Пройден полный путь всех ролей на свежей копии prod-данных, без реальных уведомлений. |
| 8. Production cutover и наблюдение | 5% | не начато | Prod переключен на Postgres, smoke-check пройден, rollback готов и задокументирован. |

## Детальный Порядок

### 1. Синхронизировать миграционную ветку

1. Убедиться, что рабочая копия чистая.
2. Подтянуть `origin/main`.
3. Влить актуальный `main` в `migration/postgres-foundation`.
4. Разрешить конфликты только в пользу актуальной prod-логики.
5. Запустить:
   - `npm test`
   - `git diff --check`

Go/no-go:

- идти дальше можно только если тесты проходят;
- если конфликт затрагивает статусы, отчеты, Telegram или авторизацию,
  остановиться и отдельно описать риск.

### 2. Обновить migration staging свежими prod-данными

1. Снять backup текущего prod `data/db.json`.
2. Скопировать JSON только в migration staging.
3. Поднять чистую staging Postgres-БД.
4. Прогнать:
   - `npm run db:migrate`
   - `npm run db:import-json`
   - `npm run db:verify-parity`
5. Удалить временный JSON с PII после проверки.

Проверить паритет:

- `shifts`;
- `applications`;
- `inviteGroups`;
- связи участников групп;
- mentor report fields;
- статусы;
- даты обучения;
- телефоны;
- `experience`;
- архив рабочих групп.

### 3. Доделать event log

События должны появляться для:

- создания заявки;
- назначения даты из очереди;
- подтверждения выхода;
- отправки рабочей группы;
- отметки `Вышел`;
- отметки `Не вышел`;
- отчета наставника;
- результата `passed/failed`;
- статуса доставки результата наставника;
- отчета самого стажера;
- отката этапа;
- отмены стажировки конкретному стажеру;
- возврата в предварительную запись;
- закрытия/отмены даты;
- авто-закрытия даты;
- изменения количества мест;
- изменения состава рабочей группы;
- изменения внутреннего комментария;
- отметки `Опытный стажер`.

Проверка:

- unit-тест на каждый тип события;
- тест, что duplicate submit не создает повторный финальный отчет;
- тест, что событие содержит actor и application id.

### 4. Перевести команды записи на Postgres в staging

Каждая команда должна стать транзакцией:

```text
validate role/initData
-> begin transaction
-> read affected rows with lock
-> validate state transition
-> write domain rows
-> write application_events
-> commit
-> return fresh state from Postgres
```

Команды:

- create/update application;
- assign from queue;
- set application status;
- send invite group;
- mark attendance;
- mentor report result;
- step back;
- cancel internship;
- cancel/close shift;
- update seats;
- mark experienced;
- clear state only for admin/recruiter with explicit confirmation.

Проверка:

- конфликт версий возвращает `409`;
- двойной клик не создает дублей;
- нельзя уменьшить места ниже занятых;
- отчет наставника не может дважды финализировать одну заявку;
- список наставника обновляется после отчета.

### 5. Добавить outbox для Telegram

В транзакции писать не прямую отправку, а задачу:

```text
notifications(status='pending')
```

Worker:

1. берет pending;
2. отправляет Telegram;
3. пишет `sent`, `failed` или `skipped`;
4. сохраняет ошибку без секретов;
5. делает retry по безопасным ошибкам.

Проверка:

- в `dry_run` ничего реально не отправляется;
- в live сообщение не теряется между DB и Telegram;
- можно увидеть, почему стажер не получил уведомление.

### 6. Full QA на staging

Обязательные сценарии:

- новая запись стажера на дату;
- запись в предварительную очередь;
- поиск в очереди;
- назначение из очереди;
- подтверждение рекрутом;
- отправка рабочей группы нескольким стажерам;
- шаблон рабочей группы по лофтам/группам;
- отметка `Вышел`;
- отчет наставника;
- итог стажеру;
- исчезновение стажера из списка наставника после отчета;
- автозакрытие даты;
- реестр;
- экспорт;
- архив групп;
- откаты;
- отмена стажировки конкретному стажеру;
- изменение мест;
- плохая ссылка;
- пустые поля;
- двойная отправка;
- старая версия state;
- проверка прав стажер/рекрут/наставник;
- светлая/темная тема;
- телефон/ноутбук.

### 7. Production cutover

Перед cutover:

1. объявить короткое окно без изменений;
2. сделать backup:
   - `data/db.json`;
   - git commit;
   - `.env` без публикации;
   - docker compose;
   - Postgres dump, если база уже существует;
3. импортировать свежий JSON в production Postgres;
4. проверить counts/parity;
5. переключить `BOOKING_STORAGE_MODE=postgres`;
6. запустить контейнер;
7. проверить `/api/health`;
8. пройти минимальный smoke:
   - открыть стажера;
   - открыть рекрута;
   - открыть наставника;
   - проверить реестр;
   - проверить группы;
   - проверить один dry-safe или контролируемый Telegram-сценарий.

Rollback:

- вернуть `BOOKING_STORAGE_MODE=json`;
- поднять предыдущий контейнер/commit;
- использовать backup `data/db.json`;
- не смешивать Postgres-записи обратно в JSON без отдельного конвертера.

## Текущее Следующее Действие

Следующий технический шаг: расширять writable Postgres command layer по одной
команде за итерацию. Интегрированные slices:
`create_shift`, `update_shift_capacity` и forward-переходы
`set_application_status` выполняются транзакционно в PostgreSQL, пишут
`application_events`, увеличивают `booking_state_meta.version` при реальном
изменении и проверяются live smoke внутри `npm run test:postgres`.

Следующая команда: `assign_shift`.

Перед runtime-включением Postgres-записи отдельно закрыть корректирующее
действие `Вернуть в новые заявки`: текущий JSON путь делает это через
`set_application_status -> pending`, но roadmap требует отдельную бизнес-команду
с явным решением по старой рабочей группе, площадке и архивным связям.
